# Plugin branch stack inventory

Research for [K1erans/t3code#2](https://github.com/K1erans/t3code/issues/2), part of the SDK v0 map ([#1](https://github.com/K1erans/t3code/issues/1)).

Sources: `upstream` = `pingdotgg/t3code`, fetched 2026-09-25. Unless a claim names another branch, it refers to `upstream/feat/plugin-management-ui` (the top of the stack, `221e6d2d17`). "main" means `upstream/main` at `d06f0ff104`.

## TL;DR

- The stack works as a trusted, in-process, local plugin system that does **one thing**: a plugin registers palette commands that take no arguments and return `{ message, tone }`, which shows as a toast. Everything else in the manifest (settings, views, mobileCards, web/desktop entrypoints, surfaces, requires/provides/optional, permissions) is parsed and then ignored.
- The strongest part is `packages/plugin-runtime`: a generic, Effect-scoped reconciler with atomic generations, rollback, and dependency planning, backed by a large contract test suite. Most of it (capability graph, arbitrary slots) is unused by the host today.
- The author-facing API is small: `export default function activate(api)`, where `api` has `registerCommand` and `onDispose`. It has no access to threads, projects, storage, settings, or events. A task board can't be built on it without new host APIs.
- Drift: 23 commits ahead of main and **1,666 commits behind** (merge base `b1670ac7d9`, about 2026-08-23). A dry `git merge-tree` gives **9 conflicting files and 27 hunks**. Almost all are additive collisions: new RPCs, settings fields, and imports next to new main code. `routeTree.gen.ts` (11 hunks) can be regenerated. Rebasing costs roughly half a day. The code itself isn't the risk.
- Upstream history: all four stack PRs (#7480, #7549, #7613, #8007) were closed and consolidated. A much larger successor, #8014 (`UtkarshUsername/t3code:feat/plugin-system`, 76 commits, >16k lines, with subprocess workers, capability brokers, declarative UI, and mobile cards), was **closed by maintainers on 2026-08-28** because it was too big to establish "that large trusted-plugin contract through one branch". Treat this as the main signal on scope for v0.

## Author-facing API today

The whole surface is `PluginPackageApi` in `apps/server/src/plugins/PluginPackageManager.ts`. It isn't exported from any package, so authors write untyped JS:

```ts
// t3-plugin.json: { manifestVersion: 1, id, version, apiVersion: 1,
//   entrypoints: { server: "./index.mjs" }, capabilities: ["t3.commands@1"],
//   contributes: { commands: ["<command-id>"] } }
export default function activate(api: {
  onDispose(cleanup: () => void | Promise<void>): void;
  registerCommand(
    command: {
      id: string;
      label: string;
      description?: string;
      surfaces: ReadonlyArray<"web" | "desktop" | "mobile">;
    },
    handler: () => unknown | Promise<unknown>, // must decode to { message, tone: "info" | "success" }
  ): void;
}): void | Promise<void>;
```

The host enforces these rules:

- `registerCommand` throws unless the manifest declares capability `t3.commands@1` and lists the command id in `contributes.commands`.
- Handler results are decoded against `PluginCommandInvocationResult`. Handler throws are wrapped in `PluginCommandExecutionError`.
- `onDispose` cleanups run LIFO when the plugin's scope closes, on disable, reload, or shutdown. Cleanup errors are recorded against the package.
- Activation runs inside the server process with full privileges. The Settings banner says so.

There is no typed SDK package. The runtime-level `PluginActivationContext` (`resolve`, `register(slot, …)`, `onDispose` in `packages/plugin-runtime/src/contract.ts`) is host-internal and never reaches authors. The #8014 successor did add a `t3/plugin` types module.

## Install and enable state: storage and scope

- **Install location:** `<stateDir>/plugins/<any-dir>/t3-plugin.json`, where `stateDir` = `<T3 home>/userdata` (`apps/server/src/config.ts`, main and branch). The directory name doesn't matter; the manifest `id` is the key, and duplicate ids are reported as discovery errors. Installing is a manual copy. There's no install RPC, which matches "local only".
- **Enable state:** `enabledPluginIds: PluginPackageId[]` inside `ServerSettings` (`packages/contracts/src/settings.ts`), persisted in the environment's `settings.json` by `ServerSettingsService.setEnabledPluginIds` (`apps/server/src/serverSettings.ts`). It's deliberately **not** in `ServerSettingsPatch`, so clients can only change it through `pluginPackages.enable`/`disable`. Because it's a `ServerSettings` field, it is still sent to every client in settings snapshots.
- **Scope:** per **environment** (per server), shared by all clients and users of that environment. It isn't per client, per project, or per user. Reload keeps the enabled state, and startup re-activates enabled ids. An enabled id that isn't found shows up as a discovery error.
- **Runtime scratch:** `<stateDir>/plugin-cache/<id>/<n>` is wiped at startup and shutdown. Package errors live in memory only.

## Spike rationale (brief)

`upstream/spike/plugin-runtime-comparison`: `packages/plugin-runtime-poc/DECISION.md` and `README.md`. The `-cordis`, `-effect-scope`, and `-pure` branches each isolate one variant under the same shared contract suite of 85 tests.

- **Chosen:** an Effect-scope executor plus a deterministic pure planner. Effect already runs T3 and gives each plugin owned async resources with reliable cleanup. The pure planner keeps validation, targeted restarts, atomic publication, and rollback predictable.
- **Cordis rejected:** it duplicates Effect's lifecycle system, still needs the same T3-specific planner, transaction model, and registry, adds about 300 KiB of dependencies, has ESM typing issues (rc.8), and is 15–50x slower on the 250-plugin restart micro-bench (322 ms vs 6.9 ms).
- **Pure-only rejected:** it's the simplest and fastest (0.8 ms), but it relies on manual finalizers, which are too easy to misuse.
- The POC itself said it does not load untrusted packages, wire contributions into the palette, or sandbox anything. It suggested the first public contribution types be "commands, settings, integrations, and panels".

## Implications for the map

1. **Build on the stack, don't restart.** Reuse the runtime, discovery and enable mechanics, contracts pattern, client atoms, and Settings shell by porting them onto a fresh branch from main. Don't rebase the old history.
2. **The v0 spec has to define almost the whole author surface.** The typed SDK package, screen host and bridge, plugin backend routes and storage, and thread/turn access are all missing. Today's API only makes toasts.
3. **Cut the manifest down to what v0 actually hosts.** Remove `mobileCards`, `permissions`, `views`/`settings` placeholders, and possibly the capability graph. Make `entrypoints.server` optional.
4. **Keep v0 small enough to land.** Maintainers closed #8014 for size (>16k lines). Several reviewable PRs, each with a working vertical slice, stand a much better chance than one platform branch. That successor branch (`UtkarshUsername/t3code:feat/plugin-system`, `5dc2ddcb8f`) is still worth mining for esbuild TS entrypoints, `t3/plugin` types, and declarative UI slots, but it shouldn't be adopted wholesale.
5. **Fix these whatever we build:** Settings is primary-environment-only (a multi-environment gap), there's no search, the example README is stale, and enable state is readable by every client through `ServerSettings`.
