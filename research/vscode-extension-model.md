## 1. Extension host: a separate process for trusted code

**What it is.** "The Extension Host is responsible for running extensions." There are three kinds: local Node.js (needs a `main` entry), web (a "Browser WebWorker runtime", needs a `browser` entry) and remote Node.js (in a container or remote machine). — https://code.visualstudio.com/api/advanced-topics/extension-host

**Why it is split out.** Extensions "have no access to the DOM of VS Code UI. You cannot write an extension that applies custom CSS to VS Code or adds an HTML element to VS Code UI." Running them in a separate Extension Host process is meant to "ensure that extensions cannot interfere with the stability and performance of VS Code". It also keeps the UI free to change: "to evolve, refactor, or improve VS Code, we need the freedom to make changes to the user interface." — https://code.visualstudio.com/api/extension-capabilities/overview. The extension-host page adds the goals of not "Impacting startup performance", "Slowing down UI operations" or "Modifying the UI". — https://code.visualstudio.com/api/advanced-topics/extension-host

Isolation here is about stability and API control. It is **not** a security sandbox. All extensions share one host process per kind, and that process has full Node access.

**How it is spawned (desktop).** The main process starts each local extension host as an Electron `UtilityProcess` (`WindowUtilityProcess`). — [SRC/platform/extensions/electron-main/extensionHostStarter.ts#L77](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/platform/extensions/electron-main/extensionHostStarter.ts#L77). The host always starts with an inspector port (`--inspect-port=0`, or `--inspect[-brk]` when debugging an extension). — [SRC/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts#L257-L284](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts#L257-L284)

**Crash behavior.** When the local host dies, the workbench logs which activated extensions were running in it and records the crash. It **restarts automatically** until a tracker sees 3 crashes in 5 minutes (`_TIME_LIMIT = 5 * 60 * 1000`, `_CRASH_LIMIT = 3`). After that it shows "Extension host terminated unexpectedly 3 times within the last 5 minutes." with the choices "Start Extension Bisect", "Restart Extension Host" and "Learn More". The UI window keeps running the whole time.

- Tracker: [SRC/workbench/services/extensions/common/abstractExtensionService.ts#L1545-L1566](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/abstractExtensionService.ts#L1545-L1566)
- Local handling: [SRC/workbench/services/extensions/electron-browser/nativeExtensionService.ts#L159-L226](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts#L159-L226)
- The remote host uses the same policy with "Remote Extension host terminated unexpectedly 3 times…" and asks the server for exit info with a 2s timeout: [abstractExtensionService.ts#L884-L937](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/abstractExtensionService.ts#L884-L937)
- Consequence: one extension that crashes the process takes down **every** extension in that host. Recovery is per host, not per extension. Bisect is how users find the culprit.

**Hang behavior.** The RPC layer marks a host `Unresponsive` when a request goes unanswered for `UNRESPONSIVE_TIME = 3 * 1000` ms, checking once a second. The workbench logs the change and reacts to it (for example with auto-profiling). It does not kill the host. — [SRC/workbench/services/extensions/common/rpcProtocol.ts#L102-L230](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/rpcProtocol.ts#L102-L230), [abstractExtensionService.ts#L852](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/abstractExtensionService.ts#L852)

**RPC cost.** Every API call between the extension host and the UI is async RPC. Arguments are JSON-stringified, with a replacer that pulls `VSBuffer`s out as separate binary references. — [rpcProtocol.ts#L20-L60](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/rpcProtocol.ts#L20-L60). This is why the API is `Thenable`-heavy and why data crossing between extensions on different hosts must be serializable. Commands are the cross-host channel, and "objects you pass in as parameters will be 'stringified' (JSON.stringify) before being transmitted." — https://code.visualstudio.com/api/advanced-topics/remote-extensions

## 2. Activation: lazy loading driven by declarations

- Activation events in `package.json` decide when an extension loads, so extensions start only when needed. Examples: `onCommand`, `onLanguage`, `onView`, `workspaceContains`, `onStartupFinished` (runs after startup "without slowing initialization"), and `*`. The docs discourage `*`: "use this activation event in your extension only when no other activation events combination works." — https://code.visualstudio.com/api/references/activation-events
- Since 1.74, contributed commands, languages, views, custom editors and auth providers **activate the extension implicitly**, so authors no longer list matching `onCommand:`/`onView:` events. — https://code.visualstudio.com/api/references/activation-events
- `activate()` is required. `deactivate()` is optional and must return a Promise if its cleanup is async. — https://code.visualstudio.com/api/references/activation-events

## 3. Contribution points: declarative UI plus a code entry point

- "Contribution Points are a set of JSON declarations that you make in the `contributes` field of the `package.json` Extension Manifest." Common ones: `commands`, `menus`, `keybindings`, `views`, `viewsContainers`, `configuration`, `customEditors`, `walkthroughs`, `themes`. Visibility is gated by `when` clauses over context keys. — https://code.visualstudio.com/api/references/contribution-points
- The key property: the workbench can render a command in the palette, a menu item or an empty view container **from the manifest alone**, without running any extension code. The code only loads (activation) when the user actually invokes it. The manifest is the contract the UI reads, and the code is behind it.
- Other manifest fields: `main` (Node entry), `browser` (web entry), `activationEvents`, `extensionDependencies`, `extensionPack`, `extensionKind`, and `capabilities` (`untrustedWorkspaces`, `virtualWorkspaces`). — https://code.visualstudio.com/api/references/extension-manifest

## 4. Webviews: isolated iframes and message passing

**Model.** A webview "Displays html content, similarly to an iframe." The docs say "Webviews are sandboxed from normal extension process, so all communication with the webview must use message passing." — `vscode.d.ts` `Webview.html` ([SRC/../vscode-dts/vscode.d.ts](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vscode-dts/vscode.d.ts)). The guide says "Webviews should be used sparingly and only when VS Code's native API is inadequate." — https://code.visualstudio.com/api/extension-guides/webview. The UX guidelines add "only use webviews when absolutely necessary" and list what not to build with them: promos, wizards, opening on every window. — https://code.visualstudio.com/api/ux-guidelines/webviews

**Origin model (source).**

- Each webview loads from `https://{{uuid}}.vscode-cdn.net/{{quality}}/{{commit}}/out/vs/workbench/contrib/webview/browser/pre/` by default (`webviewExternalEndpoint`). The `{{uuid}}` is a SHA-256 of `{parentOrigin, webviewOrigin}` encoded in base32. **Every webview therefore gets its own origin**, different from the workbench.
  - [SRC/workbench/services/environment/browser/environmentService.ts#L241-L249](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/environment/browser/environmentService.ts#L241-L249)
  - [SRC/base/browser/iframe.ts#L117-L128](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/base/browser/iframe.ts#L117-L128). This needs `crypto.subtle`, so webviews require a secure context.
  - [SRC/workbench/contrib/webview/browser/webviewElement.ts#L574-L587](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/webviewElement.ts#L574-L587)
- The outer iframe gets `sandbox="allow-scripts allow-same-origin allow-forms allow-pointer-lock allow-downloads"`. `allow-same-origin` is safe here because the origin is already unique. — [webviewElement.ts#L424](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/webviewElement.ts#L424)
- The outer host page (`pre/index.html`) is VS Code's own code. It creates an **inner** iframe for the extension's HTML and injects an `acquireVsCodeApi` shim. The shim throws on a second acquire, then sets `window.parent = window; window.top = window; window.frameElement = null`, which hides the host frame from extension content. — [SRC/workbench/contrib/webview/browser/pre/index.html#L205-L241](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/pre/index.html#L205-L241)
- Workbench ↔ host frame messaging runs over a `MessageChannel` port handed over at load. Messages from any other origin are dropped ("Skipped renderer receiving message due to mismatched origins"). — [webviewElement.ts#L515-L535](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/webviewElement.ts#L515-L535)

**Resource loading.**

- Webviews "cannot directly load resources from the workspace or local file system using `file:` uris". `asWebviewUri` converts a URI, and `cspSource` is the origin to put in the CSP (for example `img-src https: ${webview.cspSource}`). — `vscode.d.ts` `Webview.asWebviewUri`, `Webview.cspSource`
- `localResourceRoots` "Default[s] to the root folders of the current workspace plus the extension's install directory. Pass in an empty array to disallow access to any local resources." — `vscode.d.ts` `WebviewOptions`
- Mechanism: a **service worker** inside the webview intercepts `GET`/`HEAD` requests for resource URLs and for the remote authority. It forwards each one to the workbench (`load-resource`), which reads the file through the file service only if it sits under a root. The reply streams back as `did-load-resource[-chunk|-end]`. So resources travel over VS Code's own authenticated channel, not straight from the network, and it works the same for local and remote.
  - [SRC/workbench/contrib/webview/browser/pre/service-worker.js#L255-L395](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/pre/service-worker.js#L255-L395). The comment reads: "If we're making a request against the remote authority, we want to go through VS Code itself so that we are authenticated properly."
  - [SRC/workbench/contrib/webview/browser/resourceLoading.ts#L105-L149](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/resourceLoading.ts#L105-L149)
- `localhost:<port>` requests are also intercepted and can be redirected through `portMapping`. Port mapping does not work for WebSockets: "Websocket urls (e.g. `ws://localhost:3000`) cannot be mapped to another port." — `vscode.d.ts` `WebviewOptions.portMapping`

**CSP and capabilities.** The guide recommends a `<meta http-equiv="Content-Security-Policy">` starting from `default-src 'none'`, sanitizing all input, and disabling any capability not needed. — https://code.visualstudio.com/api/extension-guides/webview. Defaults: `enableScripts` false, `enableForms` follows `enableScripts`, `enableCommandUris` false (or an allowlist array). — `vscode.d.ts` `WebviewOptions`

**Messaging.**

- Extension → webview uses `webview.postMessage(msg): Thenable<boolean>`. `true` only means the message was posted: "A response of `true` does not mean that the message was actually received". "Messages can only be posted to live webviews". The payload must be JSON-serializable, and `ArrayBuffer`s transfer efficiently when `engines.vscode` ≥ 1.57.
- Webview → extension uses `acquireVsCodeApi().postMessage()` into `onDidReceiveMessage`. The webview "cannot post `Blob`, `File`, `ImageData`… since the extension… does not run in a browser environment."
- Source for both: `vscode.d.ts` `Webview.postMessage`, `Webview.onDidReceiveMessage`

**State and lifecycle.**

- By default the iframe is **destroyed when hidden** and recreated when shown. `getState`/`setState` hold JSON state that survives hiding. `WebviewPanelSerializer` restores panels across restarts. — https://code.visualstudio.com/api/extension-guides/webview
- `retainContextWhenHidden` keeps the iframe, with its "scripts and other dynamic content… suspended". It "has a high memory overhead and should only be used if your panel's context cannot be quickly saved and restored." — `vscode.d.ts` `WebviewPanelOptions`
- The d.ts contradicts itself on messaging a retained hidden webview. One place says "You cannot send messages to a hidden webview, even with `retainContextWhenHidden`". `postMessage` says hidden retained webviews count as "live".
- `setState` is sent to the host as `do-update-state` with a JSON-stringified payload. — [index.html#L226-L231](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/contrib/webview/browser/pre/index.html#L226-L231)

**Theming.** The workbench injects the current theme into every webview as CSS custom properties (`var(--vscode-editor-foreground)`, `--vscode-editor-font-family`/`-weight`/`-size`, …). It also adds body classes `vscode-light` / `vscode-dark` / `vscode-high-contrast`, a `data-vscode-theme-id` attribute, and a11y classes `vscode-using-screen-reader` and `vscode-reduce-motion`. — https://code.visualstudio.com/api/extension-guides/webview. Webviews cannot use VS Code's own components. They only get tokens.

## 5. Remote split: where code runs vs where UI renders

- **UI extensions** "are always run on the user's local machine". **Workspace extensions** "run on the remote machine / environment", in "a Remote Extension Host that sits in a small VS Code Server". — https://code.visualstudio.com/api/advanced-topics/remote-extensions
- "The extensions install VS Code Server on the remote OS" and "No source code needs to be on your local machine". — https://code.visualstudio.com/docs/remote/remote-overview
- `extensionKind` is an ordered preference: `["workspace"]`, `["ui","workspace"]` (prefer UI), `["workspace","ui"]`, or `["ui"]`. — https://code.visualstudio.com/api/advanced-topics/extension-host
  - When unset, **any extension with a `main` is deduced to be `workspace`**, and one with only `browser` becomes `web`. — [SRC/workbench/services/extensions/common/extensionManifestPropertiesService.ts#L262-L272](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts#L262-L272)
  - Running code learns where it is from `ExtensionKind.UI = 1 | Workspace = 2`, which says whether the extension "runs where the UI (window) runs or… remotely". — `vscode.d.ts` `ExtensionKind`
- **Webviews always render on the client:** "the Webview API is always run on the user's local machine or in the browser, even when used from a Workspace Extension." The extension runs remotely and its iframe runs locally, with `postMessage` and the resource service worker bridging the two. "By default, localhost inside a webview will resolve to a developer's local machine", so the docs recommend message passing over localhost servers, plus `asExternalUri`/`portMapping` when a server is unavoidable. — https://code.visualstudio.com/api/advanced-topics/remote-extensions
- Extensions on different hosts cannot share exported APIs. They talk only through async commands with JSON-stringified arguments. `SecretStorage` "will always store the secrets on the client side". — https://code.visualstudio.com/api/advanced-topics/remote-extensions
- Native modules: "VS Code Server runs a standard (non-Electron) version of Node.js", so binaries differ by host. — same page

## 6. Web extensions (worker host)

- A web extension declares a `browser` entry and runs in a browser WebWorker extension host. Restrictions: a single bundled file, no Node globals or libraries, "Creating child processes or running executables is not possible", and file access only through the VS Code file system API. It runs in vscode.dev, github.dev, desktop and Codespaces. — https://code.visualstudio.com/api/extension-guides/web-extensions
- In source, the web worker host is itself started from an iframe (`webWorkerExtensionHostIframe.html`) that uses the same parent-origin hashing as webviews. — [SRC/base/browser/iframe.ts#L118](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/base/browser/iframe.ts#L118)

## 7. Versioning and compatibility

- `engines.vscode` is required. "A value of `^1.8.0` means that your extension is compatible with VS Code `1.8.0` and onwards". — https://code.visualstudio.com/api/working-with-extensions/publishing-extension
  - The validator rejects a missing `engines`, rejects ranges less specific than a major version, and refuses load with "Extension is not compatible with Code {0}. Extension requires: {1}." — [SRC/platform/extensions/common/extensionValidator.ts#L256-L374](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/platform/extensions/common/extensionValidator.ts#L256-L374)
  - VS Code does not negotiate API versions at runtime. It publishes one API (`vscode.d.ts`) that only grows, and the engines range is a floor check.
  - `engines` also gates behavior, for example efficient `ArrayBuffer` transfer only when the extension targets ≥ 1.57. — `vscode.d.ts` `Webview.postMessage`
- **Proposed APIs** are unstable APIs that are "only available in Insiders distribution" and "should not be used in published extensions". Authors opt in per proposal with `"enabledApiProposals": [...]` and get types via `@vscode/dts`. Side-loaded users need `--enable-proposed-api=<id>`. — https://code.visualstudio.com/api/advanced-topics/using-proposed-api
  - In source, stable builds null out a non-builtin extension's proposals unless it is in `product.json#extensionEnabledApiProposals` or the CLI flag is set. The log says "CANNOT USE these API proposals … You MUST start in extension development mode or use the --enable-proposed-api command line flag". — [SRC/workbench/services/extensions/common/extensionsProposedApi.ts#L36-L113](https://github.com/microsoft/vscode/blob/6c106a13b4b97e3a75578fb47039bb4bb0a07c2f/src/vs/workbench/services/extensions/common/extensionsProposedApi.ts#L36-L113)
  - Experimental API is therefore a named, per-proposal opt-in, enforced by the host. It is separate from the stable surface.

## Maps onto T3

T3 has a Node server **environment** that owns the filesystem and providers, and web/desktop/mobile **clients** that connect over WebSocket, possibly through a tunnel. That is already VS Code's remote split, with the server in the "VS Code Server" role.

- **Plugin server code = workspace extension. Plugin screens = webviews.** VS Code's own default (`main` ⇒ `workspace`) says trusted Node code belongs with the workspace. T3 should run plugin server code in the environment, and in v0 **only** there. There is no need for a `ui`/client-side code kind; screens cover that need, and VS Code's list of `ui` uses (themes, keymaps) mostly maps to declarative contributions.
- **In-process vs separate host.** VS Code chose a separate process for stability and to keep the UI free to change, not for security. Its payoff is auto-restart with a 3-in-5-minutes cap, a 3s unresponsive detector, and a UI that survives. The costs are that every call is async JSON RPC and one bad extension still takes down all extensions in its host. T3's UI already runs in another process (the client), so a plugin crash cannot freeze the client. The open question is only whether a plugin can crash or block the **server's event loop**. That argues for at least one child process ("plugin host") for all plugins, VS Code-style, over in-process loading. Per-plugin processes would go beyond what VS Code does.
- **Screens: isolated iframe + SDK message port.**
  - VS Code's recipe transfers directly: a unique origin per screen, a host-owned outer frame that injects a single-acquire API and hides `parent`, a `MessageChannel`, origin-checked messages, JSON-only payloads, and a CSP starting at `default-src 'none'` built around a `cspSource`.
  - Resources should flow through the host's authenticated channel, not straight from plugin-served URLs. That is the service-worker trick, and it is what makes remote work.
  - For T3 the "host" of a screen is the client. Screen ↔ plugin-server traffic should go screen → client → existing WebSocket → server → plugin. This keeps screens working over LAN, Tailscale and the T3 Connect tunnel with no extra ports.
  - VS Code explicitly steers away from localhost servers in webviews, and port mapping cannot handle WebSockets. Plugins should never expose their own HTTP/WS port to screens.
- **Unique origins need thought on T3 web.** VS Code hosts webview frames on per-webview subdomains of `vscode-cdn.net`. T3 web is served from `app.t3.codes` or from the local `npx t3` origin (possibly a bare IP over LAN), and wildcard subdomains are not available there. `sandbox="allow-scripts"` **without** `allow-same-origin` (an opaque origin) is the realistic equivalent, with resources inlined or delivered through the SDK. Ticket #6 should decide this.
  - `crypto.subtle` and service workers both need secure contexts, and plain-HTTP LAN origins are not secure. VS Code's approach would break there.
- **Hidden-state policy.** VS Code destroys hidden webviews by default and offers `getState`/`setState` plus an opt-in `retainContextWhenHidden` with a memory warning. That fits T3's performance rule. Default to destroy, and give the SDK a small JSON state API.
- **Theming** is covered by VS Code's precedent: inject CSS custom properties plus light/dark/high-contrast and reduce-motion markers into the frame, and expose no components. This answers the map's "Screen look and feel" gap: T3 tokens as CSS variables, with no `components/ui` coupling.
- **Contributions + activation.** A declarative manifest (commands, views/screens, settings, keybindings, with `when`-style gating) lets the client render the palette, Settings → Plugins and navigation without running plugin code. The server activates plugin code lazily on first use, with implicit activation from contributions as in 1.74+. This also fits mobile: mobile reads the manifest and marks unsupported surfaces without executing anything.
- **Compatibility.** Borrow `engines.t3` as a required semver floor that the host checks at load with a clear "not compatible" message. Keep one additive API surface. Gate unstable API behind named, per-proposal opt-ins (`enabledApiProposals`) that the host enforces, rather than a single global "experimental" flag. That gives the map's "SDK stays experimental" stance a concrete mechanism.
- **Secrets and cross-plugin calls.** VS Code keeps secrets on the client side. T3 is different: the environment owns provider credentials, so plugin secrets belong in the environment's secret store. Cross-plugin calls, if they ever exist, should be async and JSON-only, like VS Code commands.
